# 分片视频上传与异步处理设计

## 目标

让主站聊天可以稳定接收最大 500MB 的本地视频，避免一次性上传和同步 FFmpeg 处理导致的超时。只有大于 20MiB 的视频由浏览器分片上传到 Zeabur 本机临时目录；20MiB 及以下视频继续使用现有普通上传。分片上传完成后接口立即返回任务状态，服务器在后台复用现有视频压缩、抽帧和分析能力，前端通过 `jobId` 轮询直至得到现有聊天流程可用的附件结果。

## 约束与明确不做的内容

- 不使用腾讯云 COS、Cloudflare R2 或其他对象存储。
- 浏览器只切片和重试，不在浏览器中运行 FFmpeg。这样避免 184MB 视频在用户电脑上转码时占用大量内存或卡死。
- 视频数据只保存在运行主站的单个 Zeabur 实例本机；不支持多实例共享上传任务。
- 服务重启或重新部署时，正在上传或处理的任务允许失败并要求用户重传。
- 图片和文档继续使用现有 `/api/upload`，只有视频切换到新流程。
- 20MiB 及以下视频也继续使用现有 `/api/upload`；只有文件大小严格大于 20MiB 才创建分片任务。
- 不改变聊天模型选择、视频分析结果格式或已有临时视频令牌的消费方式。

## 用户流程

1. 用户选择视频并点击发送。20MiB 及以下走现有普通上传；大于 20MiB 执行后续分片流程。
2. 前端创建上传任务，取得 `jobId`。
3. 浏览器按 5MiB 切片，最多同时上传 3 片；单片失败最多自动重试 3 次。
4. 页面显示上传百分比。已经成功的分片不会因为单片重试而再次上传。
5. 全部分片上传后，前端请求完成上传。服务器验证分片并开始后台任务，完成接口立即返回。
6. 前端每 2 秒查询任务，显示“正在合并”“正在压缩”“正在抽帧/分析”等状态。
7. 任务成功后返回与当前 `/api/upload` 视频响应兼容的附件数据，包括 `tempVideoToken`、文件大小、MIME 类型、时长、转录和关键帧等可用字段。
8. 前端继续原来的聊天发送流程，无需用户再次点击发送。

## API 协议

所有接口要求当前登录用户身份，用户只能访问自己的任务。

### 创建任务

`POST /api/video-uploads`

请求包含 `fileName`、`fileSize`、`mimeType` 和 `responseModel`。服务端验证视频必须严格大于 20MiB 且不超过 500MB，并验证扩展名和 MIME 类型；随后根据服务端配置计算分片大小及分片总数，返回 `jobId`、`chunkSize`、`totalChunks`、已接收分片列表和任务状态。浏览器以服务端返回值切片，避免前后端配置不一致。

### 上传分片

`PUT /api/video-uploads/{jobId}/chunks/{index}`

请求体是该分片的原始二进制。服务端验证用户、索引、分片长度和总文件大小，将分片写入任务专属目录。相同索引重复提交保持幂等：已存在且大小正确时直接返回成功。

### 完成上传

`POST /api/video-uploads/{jobId}/complete`

服务端根据数据库中的分片记录和磁盘文件验证完整性。缺片时返回 JSON `409` 和缺失索引；完整时将任务设为 `queued`，启动后台处理并立即返回，不等待 FFmpeg。

### 查询任务

`GET /api/video-uploads/{jobId}`

返回 `status`、`stage`、`message`、`uploadedChunks`、`totalChunks`、`uploadPercent`、成功结果或失败原因。状态为 `uploading | queued | running | succeeded | failed`；处理阶段为 `uploading | merging | compressing | analyzing | complete`。

## 服务端结构

### 数据库状态

新增 `VideoUploadJob` 和 `VideoUploadChunk` Prisma 模型。

`VideoUploadJob` 保存用户、文件元数据、回答模型、分片数量、任务状态、处理阶段、提示文字、JSON 结果、错误和时间戳。`VideoUploadChunk` 以 `(jobId, index)` 唯一临时记录已接收分片及字节数，用于可靠统计进度和幂等重试；合并成功后立即删除该任务的全部 `VideoUploadChunk` 记录。用户删除时任务级联删除。

数据库从不保存视频二进制。任务成功或失败后，`VideoUploadJob` 只为前端轮询保留最多 2 小时，随后连同残留分片记录一起删除。

### 本地临时文件

每个任务使用 `storage/video-upload-jobs/{jobId}/`：

- `chunks/{index}.part`：分片文件。
- `source.<ext>`：流式合并后的原视频。
- 后续压缩文件继续交给现有 `server-chat-video.ts` 管理。

文件名只用于展示；真实磁盘路径只使用服务端生成的 UUID 和白名单扩展名，避免路径穿越。

分片合并成功后立即删除磁盘分片和数据库分片记录；任务成功或失败后删除其余合并中间文件。超过 2 小时的任务记录和遗留目录在创建或查询任务时清理。成功产生的现有临时视频仍遵循当前 2 小时生命周期。

### 后台处理

完成接口启动当前 Node 进程内的后台 Promise，并用全局 Map 防止同一任务重复启动：

1. 按索引顺序以文件流合并分片，不把 500MB 视频整体读入内存。
2. 更新阶段为 `compressing`，调用现有 `storeUploadedVideoForModelUpload` 或 `processUploadedVideo`。
3. 对 Gemini 保留现有模型上传暂存逻辑；其他模型保留现有转录、关键帧和描述逻辑。
4. 将兼容的附件结果写入任务 JSON，状态变为 `succeeded`。
5. 捕获错误并写入简洁的中文失败信息，状态变为 `failed`。

如果轮询发现数据库任务仍在 `queued/running`，但当前进程没有对应后台 Promise，说明服务已经重启或任务上下文丢失；任务将变为失败并提示重新上传。

## Gemini 混合视频分析

Gemini 单个视频输入使用 18MiB 安全上限，避免贴近约 20MB 的提供方限制。上传任务额外保存用户当前输入的分析问题，最多 4000 个字符；为空时使用固定的通用视频拆解要求。

### 完整视频优先

后台先按现有 720p/H.264 规则压缩完整视频并读取实际输出大小：

- 输出不超过 18MiB：保留现有 `tempVideoToken`，后续聊天请求让 Gemini 直接查看完整视频。
- 输出超过 18MiB：不把超限文件发送给 Gemini，进入时间切段流程。

18MiB 是硬限制，不是尽量达到的目标。每次发送前都必须读取真实文件大小；任何超过限制的文件不得进入 Gemini 请求。

### 时间切段

上传时的 5MiB 网络分片不能直接播放，因此不能交给 Gemini。后台必须在合并原视频后，用 FFmpeg 生成可独立播放的 MP4 时间片段。

每段以约 15MiB 为目标并限制在 90 秒以内，具体时长根据完整视频的时长与压缩后大小计算。切段后逐个执行现有压缩能力并检查实际大小；仍超过 18MiB 的片段继续缩短并重切，最短 10 秒。任何片段最终仍超过 18MiB 时，任务明确失败，不发送超限内容。

每个片段记录 `segmentIndex`、`startMs`、`endMs` 和文件路径。最多同时分析 2 段，避免瞬间占满内存或触发上游限流；单段 Gemini 调用失败最多重试 2 次。

### 逐段分析与最终综合

每段发送给 Gemini 的提示包含：

- 该段准确时间范围。
- 用户当前输入的分析问题。
- 固定基础字段：画面内容、人物动作、台词与语气、镜头运动、节奏变化、情绪变化、转化设计。
- 要求返回结构化文本，并且不得推测片段中不存在的内容。

全部片段成功后，再调用一次 Gemini 文本能力综合所有分段结果。综合结果必须保留时间线、跨段衔接、主要结论和对用户问题的直接回答。任务结果的 `extractedText` 保存综合结论及必要的分段依据，供原聊天流程生成最终可见回复。

分段模式不再返回完整视频 `tempVideoToken`；聊天接口把非空 `extractedText` 视为已经解析完成的视频资料，不再要求重新附带完整视频。完整视频模式维持现有直接视频输入逻辑。

### 文件清理

单段分析成功或最终失败后立即删除该段视频和对应临时令牌。全部综合完成后删除压缩后的完整超限视频。数据库只保留任务状态、用户分析问题和最终文本结果，不保存任何视频二进制或 Base64。

## 前端结构

新增独立的视频分片上传客户端模块，负责大于 20MiB 的文件切片、最多 3 路并发、指数间隔重试、进度计算、完成通知和轮询。聊天页按 20MiB 阈值选择新模块或现有普通上传，并把状态文字展示在现有上传区域，不在页面组件中堆叠协议细节。

所有响应先检查 HTTP 状态和 `Content-Type`。如果网关返回 HTML、502、504 或超时页面，统一转换为中文错误，例如“视频分片上传失败，请检查网络后重试”，不再把 HTML 交给 `response.json()`，因此不会再显示 `Unexpected token '<'`。

同一条消息包含图片和视频时，各附件可以独立处理；只有全部附件准备完成后才发送聊天消息。视频任务失败不会清空用户输入或移除已选择文件，方便直接重试。

创建大视频任务时，前端把当前消息文本作为 `analysisPrompt` 一并提交。轮询阶段增加“正在切分视频”“正在分析第 X/N 段”“正在综合全部片段”等状态。最终任务可能返回完整视频令牌，也可能只返回非空的综合 `extractedText`；两种结果都视为处理成功。

## 配置

提供以下可选环境变量及默认值：

- `VIDEO_UPLOAD_MAX_BYTES=524288000`（500MB）
- `VIDEO_UPLOAD_CHUNK_BYTES=5242880`（5MiB）
- `VIDEO_UPLOAD_JOB_TTL_MS=7200000`（2小时）
- `GEMINI_VIDEO_MAX_BYTES=18874368`（18MiB硬上限）
- `GEMINI_VIDEO_SEGMENT_TARGET_BYTES=15728640`（单段目标15MiB）
- `GEMINI_VIDEO_SEGMENT_MAX_SECONDS=90`

现有 `VIDEO_COMPRESS_TARGET_SIZE`、FFmpeg 路径及压缩参数继续生效，不复制第二套压缩配置。

## 错误处理

- 不支持的视频格式或超过 500MB：创建任务前直接返回中文 JSON 错误。
- 单片网络失败：前端最多重试 3 次，并保留已完成进度。
- 分片缺失或大小错误：完成接口返回缺失/异常分片，不启动后台任务。
- 20MiB 及以下视频误调用创建任务接口：返回 JSON `400`，提示使用普通上传。
- FFmpeg、抽帧、转录或模型分析失败：任务进入 `failed` 并返回清理过的错误信息。
- 单段 Gemini 调用失败：最多重试 2 次，仍失败则标明片段编号和时间范围并让任务失败。
- 切段或压缩后仍超过 18MiB：不调用 Gemini，返回“视频片段压缩后仍过大”。
- 服务重启、临时文件丢失或后台任务上下文丢失：任务明确失败，提示重新上传。
- 所有接口错误都返回 JSON；前端也对非 JSON 网关错误提供兜底提示。

## 验证标准

- 测试先证明当前一次性上传实现不具备分片协议，再实施代码。
- 单元测试覆盖 20MiB 分流、文件切片、并发上限、失败重试、进度计算和 HTML 错误转换。
- API 测试覆盖身份隔离、500MB 上限、索引/大小校验、重复分片幂等、缺片拒绝和完成接口立即返回。
- 后台任务测试覆盖流式合并、合并后立即删除磁盘/数据库分片、状态阶段变化、复用现有压缩函数、成功结果、处理失败和进程上下文丢失。
- Gemini 混合策略测试覆盖完整视频低于18MiB直接处理、超限后按时间切段、每段真实大小校验、两路并发、单段重试、最终综合以及所有临时片段清理。
- 聊天测试覆盖分段模式只有 `extractedText`、没有 `tempVideoToken` 时仍能继续回答。
- 聊天流程测试覆盖视频使用新模块、图片/文档保持旧路径，以及成功后继续发送消息。
- 现有视频压缩测试必须继续通过。
- 最终运行相关专项测试、前端完整测试和生产构建；若仓库原有无关测试仍失败，须单独列明，不能混作本次回归。

## 部署与运行限制

此方案适用于当前单实例 Zeabur 服务，不需要新增外部存储。部署必须继续提供可写临时磁盘和 FFmpeg。扩容为多个实例后，本地分片无法共享，届时必须引入共享存储或请求粘性路由；本次不实现该扩展。
